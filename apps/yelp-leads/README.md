# Yelp Leads

Read and respond to Leads generated by Yelp users — new leads, conversation messages, and phone
opt-ins — for Yelp advertising and listing-management reseller partners, on the **Yelp Leads API**.

- **Categories** — marketing, crm
- **Auth methods** — oauth2
- **Actions** — 7
- **Health checks** — 2 declared absences (`service`, `quota`) + the derived `auth:oauth2`
- **Egress allowlist** — `api.yelp.com`, `partner-api.yelp.com` (`biz.yelp.com`, the browser
  authorization host, is allowed implicitly as the OAuth `authorizationUrl` host)
- **Website** — https://www.yelp.com/developers
- **API docs** — https://docs.developer.yelp.com/docs/leads-api ·
  https://docs.developer.yelp.com/reference/get-lead (and the six sibling reference pages)

> **Everything below was verified against Yelp's own sources on 2026-09-06** — the OpenAPI 3.1
> document embedded server-side in each Leads reference page at `docs.developer.yelp.com` (each
> page's own React-hydration payload, not a third-party integration directory), cross-checked
> against that page's rendered "server URL" and its prose worked example, plus live probes of
> `status.yelp.com` and `yelp.statuspage.io`.

## Access to this API is restricted

> "Access to the Leads API is currently limited to Yelp advertising and listing management reseller
> partners. Participation in these partnerships is subject to a minimum spend requirement."

That is Yelp's own overview, verbatim. Yelp's stated recommendation for anyone who isn't such a
partner is its no-code Zapier integration, which this app does not attempt to replace. A business
whose Yelp profile offers "Message the business" is explicitly *ineligible* for the Leads API per
the same overview — Yelp enforces this itself (a `403` on the affected endpoints), this app cannot
detect it in advance.

## Three findings that would have cost a day

### 1. The auth scheme is OAuth 2.0 Authorization Code — not an API key, not client-credentials

Every Leads endpoint's OpenAPI document declares `security: [{ oauth2: ["leads"] }]`. The same
document's `components.securitySchemes` also lists `basic` and `bearerAuth` entries — but neither is
ever referenced by a Leads operation's own `security` requirement; they belong to *other* Yelp APIs
(Fusion) that happen to share the same doc-generation template. Guessing from the schemes present,
rather than reading which one each operation's `security` array actually names, would have led
straight to a bearer-token app that Yelp's Leads API does not accept.

The flow itself is the business-user login dance, not machine-to-machine:

- Authorize: `GET https://biz.yelp.com/oauth2/authorize` — a *different host* from the API.
- Token exchange / refresh: `POST https://api.yelp.com/oauth2/token/v3`, form-encoded, either
  `grant_type=authorization_code&code=...` or `grant_type=refresh_token&refresh_token=...`.
- Scope: `leads` only. (`r2r`/`r2r_get_businesses`/`r2r_business_owner` are a separate
  Respond-to-Review surface this app does not touch.)
- Revoke: `POST https://api.yelp.com/oauth2/revoke`.
- Lifetimes: an authorization code expires in **5 minutes**; an access token in **7 days**; a
  refresh token in **365 days**. The **v3** token endpoint (used here) issues a **new refresh
  token on every refresh** and revokes the prior one if an expired refresh token is presented — the
  older v2 endpoint (`/oauth2/token`, not used by this app) instead keeps re-returning the same
  refresh token. Getting v2/v3 refresh semantics backwards is a documented, named gotcha
  (`docs.developer.yelp.com/docs/refresh-tokens`), not a detail Yelp buries.

### 2. There is no whoami — the health/auth probe has to be a *token-scoped business list*, not a Lead read

Every one of the seven Leads operations needs a Lead ID or a Business ID as a path parameter, and
Yelp gives no way to discover either from the access token alone. That rules out the usual
"call some cheap read with no required params" health probe entirely — there is no such call in
this surface.

The fix is a *different* Yelp host and a *different* API: `GET
partner-api.yelp.com/token/v1/businesses` ("Get Businesses Associated with Access Token") takes only
the `Authorization` header and answers `{"business_ids": [...]}`. It needs no parameter, so it works
immediately after a fresh connect, before the caller knows any Lead or Business ID — and unlike
Mailjet's `/apikey` or Follow Up Boss's `/me`, its response is a list of the caller's *own* business
ids, never the credential itself. `auth/oauth2.ts`'s `test` and `afterConnect` both use it; no
Action does, since every documented Lead/Business operation lives on `api.yelp.com`, not
`partner-api.yelp.com`.

### 3. Lead events page in *reading* order, and `limit` counts a paired attachment as one event

`GET /v3/leads/{ID}/events` returns events **oldest first, newest last** — `limit` (1-20, default
20) takes the *last* `limit` events shown on Yelp, the reverse of a typical "recent activity" feed
default. A text message sent together with an attachment produces **two** events sharing one `id`
(one `event_type: "TEXT"`, one `"ATTACHMENT_GROUPING"`), and Yelp's own `limit` semantics count that
pair as a single event — a naive count of returned array entries against `limit` would be off by one
whenever an attachment is present. Pagination is cursor-based (`older_than_cursor`/
`newer_than_cursor`), and Yelp states the cursor value is "not guaranteed to be unique or consistent
over time" — it is a paging token, not a stable event identifier; use each event's own `id` for that.

## Actions

| Key | Type | Description |
|---|---|---|
| `get-lead` | read | Read details for a given Lead ID. |
| `get-lead-events` | search | List the events (messages, attachments, other interactions) on a lead. |
| `write-lead-event` | perform | Send a text-message reply into an existing lead's conversation. |
| `mark-lead-as-replied` | perform | Mark a lead as replied through a channel outside the Leads API (phone or email). |
| `mark-lead-event-as-read` | perform | Mark a lead event, and every event before it, as read. |
| `get-lead-ids-for-business` | search | List the Lead IDs a Yelp business has received, optionally filtered by time. |
| `get-lead-metrics` | read | Read a lead's cost metrics (currently: cost per lead). |

These are exactly the seven operations in the Leads API's own OpenAPI `paths` object — nothing was
added beyond what Yelp documents. `write-lead-event` sends `request_type: "TEXT"` as a fixed literal
rather than a user choice, because the schema's enum for that field currently has exactly one member
("Currently, only text messages are supported" — Yelp's own words).

### Idempotency

`write-lead-event` and `mark-lead-as-replied` are marked **not** idempotent: Yelp itself documents a
`400 SAME_SUCCESSIVE_MESSAGE` for a repeated message within an hour, and a `403 NOT_AUTHORIZED
"Lead already marked as replied"` for a repeated mark-as-replied — a retry does not quietly repeat
the original success, it errors differently. `mark-lead-event-as-read` **is** marked idempotent:
Yelp's OpenAPI document lists no "already marked as read" error for that endpoint, so re-marking the
same or an earlier event as read is a documented no-op.

## Health check

Three questions get confused with each other, so this section keeps them apart: is the *vendor* up,
is *this credential* live, and do we have *quota* left.

### Is Yelp up?

**Declared unavailable.** Checked live 2026-09-06, two candidate hosts, both dead ends:

```
GET https://status.yelp.com/                    -> 403, empty body
GET https://status.yelp.com/api/v2/summary.json -> 403, empty body (same with/without a browser UA)
GET https://yelp.statuspage.io/api/v2/summary.json
    -> 401, "Your page is a private page. Please include an API key to access this resource."
```

`status.yelp.com` answers a bare 403 on every path tried — an edge/WAF block against server-side
clients, the same signature this pack's `campaignmonitor` app already documented for its own status
host. `yelp.statuspage.io` is a **genuinely-claimed** Atlassian Statuspage instance (an unclaimed
decoy would 302 to statuspage.io's own marketing page instead — this doesn't), but Yelp has made it
private, the same "claimed but access-gated" shape as this pack's `deel` app. Neither host offers
anything this app could probe unauthenticated. `severity: "informational"` — an `unavailable` entry
always reports `unknown`, which outranks `ok` in a roll-up, so any other severity would pin this App
at `unknown` forever.

### Is this credential live?

`GET partner-api.yelp.com/token/v1/businesses` — see finding #2 above. Distinguishes a rejected
token from a live one without ever needing a Lead or Business ID, and its response carries no
credential material.

### Do we have quota left?

**Declared unavailable.** "All the Leads API endpoints have a default rate limit of 5 requests per
second per client per endpoint" (`docs.developer.yelp.com/docs/leads-api`, "Rate Limiting") — a
fixed prose-only ceiling, not a consumable balance. All seven operations' response schemas were read
in full on 2026-09-06 and none declares an `X-RateLimit-*`/`RateLimit-*` header, so there is nothing
to read for remaining headroom.

## Deliberately out of scope

- **Business Subscriptions API** (`POST /v2/businesses/subscriptions`, subscription type
  `WEBHOOK`) — the mechanism a partner uses to *start* receiving Lead webhooks. It is a distinct
  API (`docs.developer.yelp.com/docs/business-subscriptions-api`) with its own OpenAPI document and
  its own quota surface (`YELP_KNOWLEDGE` subscriptions only), not part of the Leads OpenAPI
  document this app was built from. It belongs in its own app rather than a parallel copy here.
- **Leads Webhooks themselves** (`docs.developer.yelp.com/docs/leads-webhooks`) — the inbound
  notification a partner *receives*, not a call this app makes. w6w Apps declare `triggers` for
  inbound events; this v1 covers the Leads read/write surface only, per the contract's scope.
- **Respond-to-Review** (`r2r`/`r2r_get_businesses`/`r2r_business_owner` scopes) — a related but
  separate OAuth-scoped surface on the same authorization flow, outside the Leads API proper.
