# Process Street

Start and manage **Process Street** Workflow Runs (the vendor's UI still calls these
"checklists"), their tasks and form field values, over the **Process Street Public API v1.1**.

- **Categories** — productivity, project-management
- **Auth methods** — api-key
- **Actions** — 15
- **Health checks** — 2 (`service`, `quota`) + the derived `auth:api-key`
- **Egress allowlist** — `public-api.process.st`
- **Website** — https://www.process.st/
- **API docs** — https://public-api.process.st/api/v1.1/docs

> **Everything below was verified against Process Street's own OpenAPI 3.1 document** — fetched
> directly from `public-api.process.st/api/v1.1/docs/docs.yaml` (2.3MB) on 2026-09-06 — plus live
> probes of `public-api.process.st` and `status.process.st`. Nothing here came from a third-party
> integration directory.

## The three things most likely to cost someone a day

### 1. The documented `referenceId` idempotency key for starting a run does not exist on the wire

The spec's own prose says: "`POST` is generally not safe to blindly retry. For workflow runs,
attach a `referenceId` on create — calling `createWorkflowRun` twice with the same `referenceId`
will return the existing run instead of creating a duplicate." **`CreateWorkflowRunRequest`'s
actual schema has exactly four properties: `workflowId`, `name`, `dueDate`, `shared` — no
`referenceId` field exists anywhere on it.** Sending one is a silently-ignored extra field, not a
dedupe key. [`workflow-run-create`](actions/workflow-run-create.ts) is marked `idempotent: false`
accordingly and does not pretend the field works — a retry after a timeout WILL create a duplicate
run.

### 2. Two different "list workflow runs" endpoints, with different pagination AND a different response envelope key

`GET /workflow-runs` ("Search workflow runs") answers "the latest 200 workflow runs of a workflow"
— **no `_` cursor parameter, no `links[]` at all, hard-capped at 200 results** — and wraps its
array under `{"workflowRuns": [...]}`. `GET /workflow-runs/list` ("List all workflow runs") is the
real cursor-paginated endpoint, sorted newest-created-first, and wraps the identical item shape
under `{"data": [...]}` instead. Code written against one and pointed at the other will either
silently truncate at 200 results or read `undefined` off the wrong key. This app exposes both under
clearly different names — [`workflow-run-search`](actions/workflow-run-search.ts) (the capped one,
which is also the only one that can filter by `name` or by a form field's value) and
[`workflow-run-list`](actions/workflow-run-list.ts) (the paginated one) — rather than picking one
and hiding the gap.

### 3. Real rate-limit headers exist and are completely undocumented — and `Retry-After` is not delta-seconds

The spec's only rate-limit guidance is one sentence: "wait for the duration specified in the
`Retry-After` header." **Verified live 2026-09-06** against `GET /testAuth`: every response —
including a 401 from a garbage key — actually carries `X-Ip-Rate-Limit-{Limit,Remaining,Reset}`
(keyed by caller IP) and `X-Api-Key-Rate-Limit-{Limit,Remaining,Reset}` (keyed by the literal key
string sent; even a fake key gets its own fresh 2500-request bucket) — none of the four appear
anywhere in the 2.3MB OpenAPI document. `Retry-After` was also observed as an **HTTP-date**
(`Sun, 06 Sep 2026 20:04:44 GMT`), not the delta-seconds format that header name is usually
assumed to carry. [`health/quota.ts`](health/quota.ts) reads the per-key trio.

## A smaller vendor quirk, documented at the call site

**Auth-failure bodies carry no `errorCode`**, contradicting the spec's own advice to "branch on
`errorCode` rather than regex'ing `error`". Verified live: a missing key on `GET /testAuth` answers
`401 {"error":"Unauthorized"}`; an invalid key answers `401 {"error":"Unable to verify
credentials."}` — neither carries `errorCode`, `requestId`, or `details`. The spec's own prose
explains why: `errorCode`/`requestId` are populated "on responses generated by the public API
exception handler," but a low-level auth rejection is exactly the case that bypasses it. Both
[`auth/api-key.ts`](auth/api-key.ts)'s `test` hook and [`lib/client.ts`](lib/client.ts)'s
`errorMessage` fall back to the raw `error` string rather than assuming a machine-parsable code —
for the single failure mode a health/auth probe cares about most.

## Auth

**API Key** (`X-API-Key` header — the spec's `apiKeyAuth` security scheme), generated from
Organization Settings in the Process Street app. "Each key carries the permissions of the user
that created it" (spec prose). A second, beta `httpAuth` bearer scheme is also declared in the spec
but documented only as "Bearer token (beta)" with no further detail — not implemented here.

`GET /testAuth` returns only `{"apiKeyLabel": "..."}` — the key's own human-assigned label, never
the key itself — so it's safe to use as both the liveness probe and the `quota` check's data
source.

## Health

- **`service`** — Atlassian Statuspage at `status.process.st/api/v2/summary.json`, verified live as
  genuinely Process Street-operated (`page.name: "Process Street"`). The page has exactly two
  components: **`"Process Street APIs"`** (what this check reports) and `"Process Street Web
  Application"` (the app.process.st product UI, unrelated to this API and ignored).
- **`quota`** — the undocumented `X-Api-Key-Rate-Limit-{Limit,Remaining,Reset}` headers (see finding
  #3 above), read off the same `GET /testAuth` call the auth `test` hook already makes.
  `informational` severity: running low is worth showing, never worth failing a verdict over.
- **`auth:api-key`** (derived) — `GET /testAuth`. Never echoes the key back, so it's safe to use as
  the liveness probe.

## Actions

**Workflow** (the reusable blueprint — tasks/form fields/logic; read-only in this app):
- [`workflow-list`](actions/workflow-list.ts) — `GET /workflows`, 20 at a time, cursor-paginated.
- [`workflow-get`](actions/workflow-get.ts) — `GET /workflows/{workflowId}`.

**Workflow Run** (one running instance of a Workflow — what the product UI calls a "checklist"):
- [`workflow-run-create`](actions/workflow-run-create.ts) — `POST /workflow-runs`. Starts a run.
  See finding #1 — **not** safely retryable.
- [`workflow-run-list`](actions/workflow-run-list.ts) — `GET /workflow-runs/list`. The real
  cursor-paginated listing. See finding #2.
- [`workflow-run-search`](actions/workflow-run-search.ts) — `GET /workflow-runs`. Filterable by
  `name`/form-field value; capped at 200 results, not paginated. See finding #2.
- [`workflow-run-get`](actions/workflow-run-get.ts) — `GET /workflow-runs/{workflowRunId}`.
- [`workflow-run-delete`](actions/workflow-run-delete.ts) — `DELETE /workflow-runs/{workflowRunId}`.
  A 404 (already deleted) is treated as success, per the spec's own idempotency rule.

**Task** (a step within one Workflow Run):
- [`task-list`](actions/task-list.ts) — `GET /workflow-runs/{workflowRunId}/tasks`, cursor-paginated.
- [`task-get`](actions/task-get.ts) — `GET /workflow-runs/{workflowRunId}/tasks/{taskId}`.
- [`task-complete`](actions/task-complete.ts) / [`task-uncomplete`](actions/task-uncomplete.ts) —
  `PUT /workflow-runs/{workflowRunId}/tasks/{taskId}` with `{status: "Completed"}` /
  `{status: "NotCompleted"}`. Documented idempotent.
- [`task-list-by-assignee`](actions/task-list-by-assignee.ts) — `GET /tasks`. Cross-workflow "what's
  assigned to X" lookup; `assigneeEmail` is a **required** query param — there is no "list every
  task in the account" call.

**Form field values** (data a Workflow Run collects):
- [`form-field-list`](actions/form-field-list.ts) — `GET /workflow-runs/{workflowRunId}/form-fields`.
- [`form-field-set`](actions/form-field-set.ts) — `POST /workflow-runs/{workflowRunId}/form-fields`.
  Field ids omitted from the request are left unchanged (never appended-to as a collection).
  Functionally idempotent despite being a `POST`. The per-field value shape depends on field type
  (`value` for Short Text/Long Text/Email/Website/Dropdown/Date/a single Members value/a Data Set
  row id; `values` for Multi Select/Multi Choice/multiple Members; `dataSetRowId` as an alternative
  to `value` for a Data Set Linked Dropdown) — exposed as a single `json`-typed `fields` param
  matching `UpdateMultipleFormFieldValuesRequest` verbatim, rather than one param per field type.

**User**:
- [`user-list`](actions/user-list.ts) — `GET /users`, 20 at a time, cursor-paginated.

## Out of scope

Real v1.1 surfaces, deliberately left out to keep this app to the checklist/workflow-run/task core:

- **Pages and Page Revisions** — a separate content-document surface (no tasks/form fields), plus
  their own permissions, widgets, and publish flow.
- **Workflow blueprint editing** — creating/publishing workflow revisions, tasks, widgets, logic
  rules, due-date rules, assignment/permission rules. This app only reads blueprints
  (`workflow-list`/`workflow-get`) and runs them; it does not build or edit them.
- **Data Sets** and their incoming webhooks/records — a separate structured-data feature.
- **Comments** and **Attachments** on tasks.
- **Approvals** (`/workflow-runs/{id}/approvals`) and **Assignees**
  (`/workflow-runs/{id}/assignees`, `/tasks/{id}/assignees`).
- **Webhooks** (outgoing) and **Scheduled Workflows** (recurring auto-starts).
- **The `/work/*` surface** — a separate "my assigned work" view (items/stats/snooze) distinct from
  the Workflow Run-scoped task model this app covers.
- **File uploads and form-field file attachments** (`/file-uploads`,
  `/workflow-runs/{id}/form-fields/{id}/upload`).
