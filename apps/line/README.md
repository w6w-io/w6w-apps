# LINE

Send and receive messages through the **LINE Messaging API** — the API a LINE Official Account
(a business/creator account on LINE, the dominant chat platform in Japan, and widely used across
Taiwan, Thailand and Indonesia) uses to talk to its users.

- **Categories** — communication, marketing
- **Auth methods** — channel-access-token (`bearer`)
- **Actions** — 17
- **Health checks** — 2 (`service`, `quota`) + the derived `auth:channel-access-token`
- **Egress allowlist** — `api.line.me`, `api-data.line.me` (the `service` health check adds
  `api.line-status.info` to its own hook allowlist, never to the app's)
- **Website** — https://line.me/
- **API docs** — https://developers.line.biz/en/reference/messaging-api/

> **Not to be confused with**: this is the LINE **Messaging API** only. LINE Login, the LINE
> Front-end Framework (LIFF), and LINE's other developer products are separate APIs with separate
> hosts and are out of scope for this app entirely.

> Everything below was verified on 2026-09-05 against the vendor's own reference **source**
> (`github.com/line/line-developers-docs-source`, `docs/en/reference/messaging-api/index.html.md`,
> ~694,000 bytes) plus live probes against `api.line.me` and `api.line-status.info`. The rendered
> [reference page](https://developers.line.biz/en/reference/messaging-api/) renders its endpoint
> detail client-side (a Nuxt app), so the markdown source it is built from was fetched directly
> rather than scraping the rendered HTML for accuracy.

## Findings worth recording

### 1. Two hosts, and the split is exact and small

The reference's very first "Common specification" is a table naming which host each endpoint
lives on: `api.line.me` for everything, **except** five endpoints that move large binary payloads,
which live on `api-data.line.me` instead — content retrieval, the two rich-menu-image endpoints,
and the two upload-by-file audience endpoints. This app implements two of those five (content
retrieval, rich-menu image upload) and needs `api-data.line.me` in `w6w.network.allow` for exactly
those two actions — every other action stays on `api.line.me`.

### 2. The vendor's own status page is scoped wider than this API — and this matters for the check

LINE publishes a real, live Atlassian Statuspage at **`api.line-status.info`** (linked from the
Messaging API reference itself), confirmed three ways: a nonsense sibling path 404s (not a
catch-all), the page self-identifies as `"LINE API"`, and it carries a genuine **"Messaging API"
group** with two children, `API` and `Webhook`. But the *same page* also carries **LINE Login**,
**LINE Front-end Framework (LIFF)**, and the **Developers Site/Console** as entirely separate
top-level components this app has nothing to do with. Scoring the page's worst component (the
naive approach) would report this app degraded because LINE Login is having a bad day —
`health/service.ts` reports only the "Messaging API" group's own two children instead, pinned by a
test asserting that an outage on LINE Login leaves this app's verdict at `ok`.

### 3. LINE's own idempotency key needs a caller-minted UUID — so this app doesn't invent one

Push, multicast and broadcast messages all accept an optional `X-Line-Retry-Key` header that LINE
uses to deduplicate a retried send — a real, documented idempotency mechanism. But the key has to
be "a UUID in hexadecimal format... generated by any method. The retry key isn't generated by
LINE." The host's own `ctx.invocation.invocationId` is a prefixed string (`inv_...`), not a UUID,
so silently substituting it and declaring these actions `idempotent: true` would be dishonest — a
non-UUID value in that header is simply not what LINE's dedup keys on. Instead, `retryKey` is an
optional, caller-supplied param (see `lib/params.ts`), and `message-reply`/`message-push`/
`message-multicast`/`message-broadcast` are all declared `idempotent: false`. `message-reply` has
no retry key at all — a reply token is single-use, so a retry after the first attempt actually
succeeded fails outright with `400 Invalid reply token`.

## Auth

One method: `channel-access-token`, type `bearer`, header `Authorization: Bearer <token>`.

LINE documents **four** ways to obtain a channel access token: long-lived (minted once by hand in
the Developers Console, no expiry until revoked), short-lived (30 days,
`POST /v2/oauth/accessToken`), stateless (15 minutes, `POST /oauth2/v3/token`), and v2.1 (a
caller-chosen expiry, `POST /oauth2/v2.1/token`, requiring a JWT assertion signed with a private
key registered to the channel). This app supports only the first. The other three are all
*issuance* flows this app deliberately does not implement — see "Deliberately not covered" below.

### The probe is `GET /v2/bot/info`

Chosen by reading the response schema and confirming live, not by its name:

| Check | Result |
| --- | --- |
| Requires a credential? | Yes — unauthenticated: `401 {"message":"Authorization header required. Must follow the scheme, 'Authorization: Bearer <ACCESS TOKEN>'"}` |
| A wrong-but-plausible token? | A *different* `401`: `{"message":"Authentication failed. Confirm that the access token in the authorization header is valid."}` — `test` reports these two cases distinctly rather than collapsing them |
| Leaks anything? | No — the documented response is `{userId, basicId, premiumId?, displayName, pictureUrl?, chatMode, markAsReadMode}`, the account's own public identity, never the token or anything that could be replayed as one |
| Needs a scope the credential might lack? | No — LINE channel access tokens are not endpoint-scoped, so any live token reaches it |

17 actions.

| Key | Type | Endpoint |

| `bot-info-get` | read | `GET /v2/bot/info` |
| `profile-get` | read | `GET /v2/bot/profile/{userId}` |
| `message-reply` | perform | `POST /v2/bot/message/reply` |
| `message-push` | perform | `POST /v2/bot/message/push` |
| `message-multicast` | perform | `POST /v2/bot/message/multicast` |
| `message-broadcast` | perform | `POST /v2/bot/message/broadcast` |
| `message-quota-get` | read | `GET /v2/bot/message/quota` |
| `message-quota-consumption-get` | read | `GET /v2/bot/message/quota/consumption` |
| `content-get` | read | `GET /v2/bot/message/{messageId}/content` (on `api-data.line.me`) |
| `rich-menu-create` | perform | `POST /v2/bot/richmenu` |
| `rich-menu-list` | search | `GET /v2/bot/richmenu/list` |
| `rich-menu-get` | read | `GET /v2/bot/richmenu/{richMenuId}` |
| `rich-menu-delete` | perform | `DELETE /v2/bot/richmenu/{richMenuId}` |
| `rich-menu-image-upload` | perform | `POST /v2/bot/richmenu/{richMenuId}/content` (on `api-data.line.me`) |
| `rich-menu-set-default` | perform | `POST /v2/bot/user/all/richmenu/{richMenuId}` |
| `rich-menu-link-to-user` | perform | `POST /v2/bot/user/{userId}/richmenu/{richMenuId}` |
| `rich-menu-unlink-from-user` | perform | `DELETE /v2/bot/user/{userId}/richmenu` |

### Message content is LINE's own JSON, not a re-modelled form

`message-reply`/`push`/`multicast`/`broadcast` all take a `messages` param: a JSON array of up to 5
of LINE's own ["message objects"](https://developers.line.biz/en/reference/messaging-api/#message-objects)
(`text`, `image`, `video`, `audio`, `location`, `sticker`, `imagemap`, `template`, `flex`), rather
than one typed action per message type. LINE's schema already covers dozens of shapes across nine
message types, each with its own nested field set (a `flex` message alone is an entire mini
layout language) — re-deriving each as a separate form would multiply this app's action count
without adding anything the vendor's own object model doesn't already say, the same reasoning
Apify's `actorInputParam` uses for a payload this app doesn't own the schema of. Likewise,
`rich-menu-create`'s `areas[].action` reuses LINE's whole tap-action union.

### Idempotency

- **`message-reply`**: `idempotent: false` — a reply token is single-use; retrying after a
  successful first attempt fails with `400 Invalid reply token`. No retry-key mechanism exists for
  this endpoint at all.
- **`message-push`/`multicast`/`broadcast`**: `idempotent: false` by default (see Finding 3 above);
  supply the optional `retryKey` param yourself for LINE-side dedup on retries.
- **`rich-menu-create`**: `idempotent: false` — every call creates a new rich menu with a new ID.
- **`rich-menu-image-upload`**: `idempotent: false` — LINE's own note: "You can't replace an image
  set to a rich menu"; a second upload to the same rich menu ID fails outright.
- **`rich-menu-delete`**: `idempotent: true` — a 404 on a retry (already deleted) is treated as the
  same successful end state, not an error.
- **`rich-menu-set-default`/`link-to-user`/`unlink-from-user`**: `idempotent: true` — each
  converges on the same end state (a link/no-link) no matter how many times it runs.

## Health checks

Two declared checks plus the derived `auth:channel-access-token`.

### `service` — real, and scoped to the Messaging API group only

See Finding 2 above. `credential: "none"`, `network.allow: ["api.line-status.info"]` on the hook
only (never the app's manifest).

### `quota` — combines two reads into one headroom answer

`GET /v2/bot/message/quota` (`{type: "none"|"limited", value?}`) and
`GET /v2/bot/message/quota/consumption` (`{totalUsage}`) together answer "how much of this month's
sending allowance is left". `type: "none"` means no ceiling is *configured* — most LINE plans meter
by paid-per-message rather than a hard cap — so it is reported `ok` (unmetered) rather than
exhausted; reading it the other way would report every unlimited account as broken. A configured
limit at or above 90% consumed reports `degraded`; at 100% reports `down`.

## Deliberately not covered

LINE's Messaging API surface is large. What is left out, and why:

- **The other three token-issuance flows** (short-lived, stateless, v2.1) — see Auth above. All
  three either expire on a fixed schedule this app has no background renewal process for, or need
  private-key JWT signing that a network-less, credential-only `sign` hook cannot perform. A
  long-lived token from the Console is also what every other first-party LINE integration
  (Zapier, Make, n8n) asks for, for the same reason.
- **Narrowcast messaging** (`/v2/bot/message/narrowcast` and its progress/validate endpoints) —
  targets recipients by demographic filter or audience (retargeting) objects, a materially
  different and larger request shape than push/multicast/broadcast, and delivers asynchronously
  (its own success response does not mean delivery succeeded).
- **Audience management** (`/v2/bot/audienceGroup/**`) — creating/uploading/managing retargeting
  audiences, including the two endpoints that live on `api-data.line.me` for by-file uploads. A
  large, separate feature area in its own right.
- **Insights** (`/v2/bot/insight/**`) — demographics, follower counts, delivery/read statistics,
  rich menu analytics.
- **Coupons** (`/v2/bot/coupon/**`) and **Membership** (`/v2/bot/membership/**`) — LINE-specific
  monetization features, both JP-market-only per the vendor's own documentation.
- **Group/room chat management** (leave, member list/count/profile) and **multi-person chat**
  equivalents — reachable, just not included in this first cut; straightforward additions later
  following `profile-get`'s pattern.
- **Rich menu aliases and batch control** (`/v2/bot/richmenu/alias/**`, `/richmenu/batch`,
  `/richmenu/bulk/link`, `/richmenu/bulk/unlink`) — the basics (create/list/get/delete,
  set-default, per-user link/unlink) are covered; the bulk/alias variants are the same operations
  at a different scale.
- **Message validation endpoints** (`/v2/bot/message/validate/*`) — a dry-run check for a message
  array before sending it. Useful, but additive rather than core.
- **Webhook management and signature verification** (`/v2/bot/channel/webhook/*`, and validating
  the `x-line-signature` header on an inbound webhook) — this app declares no `triggers`, so it
  never receives a webhook to verify. Left for a future project that adds trigger support.
- **Getting a preview image / transcoding status for video-audio** (`/content/preview`,
  `/content/transcoding`) — both on `api-data.line.me` alongside `content-get`, and both real,
  simple additions; left out only for this first cut's scope.
- **`GET /v2/bot/followers/ids`, `GET /v2/bot/insight/demographic`, and other listing
  endpoints not named above** — omitted for the same reason: this cut targets the core
  reply/push/broadcast/profile/rich-menu path, not full API coverage.

Nothing above was left out because it could not be confirmed — every endpoint named is documented
in the vendor's own reference and was read there.

## Icon

`assets/icon.svg` is the vendor's mark, used **verbatim** from
[simple-icons](https://github.com/simple-icons/simple-icons/blob/develop/icons/line.svg) — 1176
bytes, a single black path titled "LINE", unmodified. A test asserts its exact byte length and
that its `<title>` and opening `<svg>` tag are unchanged.

```
│   ├── client.ts                   # LineClient (both hosts), error formatting, base64 helpers

```

## Development

From this directory, inside the `api` container:

```bash
deno task validate   # manifest + sandbox-rule audit (_tools/audit.ts)
deno task check       # typecheck
deno task lint
deno task fmt         # never bare `deno fmt` — the task's file list excludes assets/
deno task test
```
