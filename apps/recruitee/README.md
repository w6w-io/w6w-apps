# Recruitee

Manage candidates, job offers, notes, tasks, tags and the hiring pipeline in **Recruitee**, an
applicant tracking system (ATS), over its REST API.

- **Categories** — hr
- **Auth methods** — api-token
- **Actions** — 17
- **Health checks** — 2 (`service`, ~~`quota`~~) + the derived `auth:api-token`
- **Egress allowlist** — `api.recruitee.com` (the `service` check adds `status.tellent.com` to its
  own hook allowlist, never to the app's)
- **Website** — https://recruitee.com/
- **API docs** — https://apidocs.recruitee.com (redirected from `api.recruitee.com/docs/index.html`,
  which only does a client-side JS redirect and never shows up as an HTTP redirect via `curl`)
- **Status page** — https://status.tellent.com/ (`status.recruitee.com` 301s here)

> **Everything below was verified two ways on 2026-09-05**: against `apidocs.recruitee.com`'s own
> recorded request/response examples, AND live against `api.recruitee.com` with no credential and
> with a syntactically-plausible bad bearer token. The second check is load-bearing — see finding
> #1.

## The three things most likely to cost someone a day

### 1. The published "API docs" page documents Recruitee's entire private web app, not a public API

`apidocs.recruitee.com` is generated by `rspec_api_documentation` directly from Recruitee's Rails
request specs. Parsed in full, it documents **951 actions across 247 resource groups** — and
nothing in the document itself marks which of those a third-party integration can actually call.
Sitting right alongside the candidate/offer/task resources this app uses are `Admin.Web.Admin`
(whose own doc text for the un-scoped `GET /admin` says "Use HTTP Basic Authentication, Username:
email, Password: password" — an account password, not a token), `Billing.Web.*`, `GDPR.Web.*`, the
entire `Referral.Portal.Web.*` surface, and `POST /c/{company_id}/oauth/personal_tokens` — the
endpoint that *mints* the very token this app signs with, called from a signed-in browser session,
never by an integration.

Trusting the document alone would have meant guessing which of 247 groups are reachable with a
personal API token. Instead, every resource this app calls was independently confirmed live:

```
$ curl -i https://api.recruitee.com/c/1/candidates
HTTP/2 401
www-authenticate: Bearer realm="recruitee"
{"error":"Resource access requires authentication!","error_code":null}

$ curl -i https://api.recruitee.com/c/1/candidates -H "Authorization: Bearer faketoken123"
HTTP/2 401
www-authenticate: Bearer realm="recruitee", error="invalid_token", error_description="Token not found."
{"error":"Token not found.","error_code":"invalid_token"}
```

That is a standard RFC 6750 bearer challenge — no cookie, no CSRF token, no Basic-auth prompt — on
every resource this app implements (candidates, offers, departments, notes, tasks, tags,
placements), and the company-scoped `GET /c/{company_id}/admin` whoami answers identically. That
consistent challenge is the evidence a personal API token is the intended mechanism for these
particular paths; nothing here was taken on the doc's authority by itself. See
[`lib/client.ts`](lib/client.ts) for the full account.

**Deliberately left out, not overlooked**: file/CV upload and parsing, requisitions, EEO data,
GDPR/consent flows, the referral portal, interview scheduling, billing, and anything under
`Admin.Web.*` — either because they need a browser session rather than a token, or because their
request-body schema is not shown anywhere in the document (only this endpoint's own flat/query
params are — never the nested resource object's own fields), and this app does not guess a body
shape it cannot point at a real example for.

### 2. Recruitee is now owned by Tellent — but the product, API and this app's name are not renamed

Recruitee's parent company rebranded to **Tellent** in 2024. Checked before keeping the name
"Recruitee" here, on 2026-09-05:

- **`recruitee.com` is still live** as its own site (not a redirect to `tellent.com`), and its own
  `<title>` reads *"Customizable ATS & hiring software | Tellent Recruitee"* — the product is
  marketed as "Tellent Recruitee", not folded into a generic "Tellent" name.
- **The API host and reference are still Recruitee's own.** `api.recruitee.com` is live and
  answers the bearer challenge above; `apidocs.recruitee.com`'s own `<title>` is plainly *"Recruitee
  API"*. `api.tellent.com` resolves but answers a bare `404` with none of the shape above — it is
  not this API under a new name.
- **The favicon is genuinely ambiguous, and this app used the one that still says "Recruitee".**
  `recruitee.com` serves *two* competing favicon links: `<link rel="shortcut icon">` points at the
  Tellent parent-brand mark (a purple "t"), while `<link rel="icon">` — which browsers generally
  prefer — points at `recruitee.com/hubfs/recruitee_fav.png`, a distinct, still-live Recruitee-only
  mark (two magenta/purple blocks) unrelated to the Tellent "t". [`assets/icon.svg`](assets/icon.svg)
  is that second one, normalized onto this pack's square canvas.
- **The vendor's own status page structurally separates the two brands.** `status.recruitee.com`
  301s to `status.tellent.com`, a Statuspage instance that bundles three product lines under the
  Tellent umbrella — but its own `"Tellent Recruitee"` component group cleanly identifies exactly
  the six components that belong to this product. See `health/service.ts`.

This is the mirror image of this pack's MessageBird→Bird case (where the API host moved to the new
brand and the app kept the *old* name only for its still-current, still-documented surface) and its
own OpenPhone→Quo case (where the API host *did* move and the app followed it). Here, nothing
customer-facing has actually moved off the Recruitee name — so the app is named, hosted and
iconed exactly as the live product is today, with this section as the paper trail if that changes.

### 3. Two candidate fields are read off response shapes, not off a documented request schema

Recruitee's "URI Parameters" doc blocks only ever list an endpoint's own flat/query params (`id`,
`company_id`, `limit`, …) — never the fields nested inside a `candidate`/`offer`/`task` request
body. `custom_fields` on `candidate-create`/`candidate-update` is exposed in exactly the
`[{"label", "values"}]` shape from the vendor's own recorded example; `emails`/`phones` are exposed
on the strength of appearing as plain string arrays on every candidate object this app reads back
(`candidate-get`, `candidate-list`), not on a request-body example that includes them. Both are
narrower than Recruitee's real candidate schema (which also has `urls`, `sources`, structured CV
`fields`, and more) — the wider set was left out rather than guessed.

## Auth

**API Token** (`bearer`) — a personal API token from *Settings → Apps and plugins → Personal API
tokens*, plus the numeric **Company ID** from the account's own Recruitee URL. The company id is not
secret, but every resource this app calls is scoped under `/c/{company_id}/...`, so it is collected
once at connect time (exactly like `packages/apps/apps/freshdesk`'s `domain` field) rather than as a
per-action param — an Action can never be pointed at a different company than the one that was
connected.

The credential probe is the company-scoped `GET /c/{company_id}/admin` — "who am I" for a bearer
token, needing no resource-specific scope, and returning only the calling admin's own id/email/role,
never a secret. The un-scoped `GET /admin` was deliberately not used: its own doc text says to
authenticate it with HTTP Basic using an account email + password, a different, legacy mechanism
this app does not touch.

## Health checks

- **`service`** (kind: `service`, informational default → `degraded`) — reads
  `status.tellent.com/api/v2/summary.json` and rolls up only the six components in that page's own
  `"Tellent Recruitee"` group, found by name each fetch (not a hardcoded component/group id) so a
  Statuspage-side id change reports `unknown` rather than silently emptying the filter. See finding
  #2 for why the page-level `status.indicator` is not used directly: it also covers two unrelated
  Tellent product lines and would report an outage on Recruitee for an incident that never touched
  it.
- **`quota`** — declared **unavailable** (`informational`, so it never pins the app at `unknown`).
  Recruitee documents no rate-limit/usage endpoint anywhere in its 247 resource groups, and a live
  request against `api.recruitee.com` carries no `X-RateLimit-*`/`RateLimit-*` response header on
  either a 401 or a successful call — checked directly, not assumed from the doc's silence.
- **`auth:api-token`** — derived automatically from the Auth method's `test` hook.

## What's out of scope

CV/cover-letter upload and parsing (file params), requisitions, EEO data collection, GDPR/consent
flows, interview scheduling, the referral portal/program, billing, and anything requiring the
signed-in-browser-only `Admin.Web.*`/`Auth.Web.OAuth.PersonalToken` surfaces — either not reachable
with a personal API token (confirmed live, not assumed), or with no request-body schema this app
could point at a real documented example for. See finding #1.
