# Vero

Identify, track, tag, alias, delete, and subscribe/unsubscribe users via Vero's write-side Track
API.

- **Categories** — email, marketing
- **Auth methods** — apiKey (Tracking API Key, `auth_token` query parameter)
- **Actions** — 7
- **Egress allowlist** — `api.getvero.com`
- **Website** — https://www.getvero.com
- **API docs** — https://help.getvero.com/api-reference/overview (redirected from
  `developers.getvero.com/?bash`, which is the URL Vero's own site links to)

## Two different Vero APIs — this app only calls one

Vero exposes two unrelated REST surfaces on the same base host (`api.getvero.com/api/v2`), and it
is easy to conflate them:

| | Track API (this app) | Campaigns API |
|---|---|---|
| Purpose | Write user profiles, properties, events, tags, subscription state | Build/manage broadcasts, journeys, preference-center topics |
| Stability | Stable since before 2016, no breaking changes | **Public preview** |
| Auth | **Tracking API Key** (`auth_token` query param) | A *separate* Campaigns API secret key, `Authorization` header |
| Access | Generated by any account | **Granted only on request** — email `support@getvero.com` |

This app implements only the Track API — the seven verbs below. The Campaigns API is not
implemented: it is a gated preview most connections will not have a key for, and its resource model
(Broadcast, Broadcast Message, Broadcast Message Content, Journey, Journey Message, Journey Message
Content, Topic — each with its own create/get/list/update endpoints) is a much larger surface than
this app's scope. Noted here rather than silently dropped.

## Auth — Tracking API Key

A single **Tracking API Key**, sent as the `auth_token` query parameter on every request
(`apiKey`, `in: "query"`). Vero's docs also document `tracking_api_key` as an alias for the same
parameter, but every code sample and the embedded OpenAPI `securitySchemes` entry
(`{ "api_key": { "type": "apiKey", "name": "auth_token", "in": "query" } }`) use `auth_token`, so
that's what this app sends.

Found under:
- **Vero 2.0** — Settings → Project → API Keys → Tracking Keys
- **Vero 1.0** — Settings → Track API Keys ("Auth Tokens" in Vero 1.0 terminology)

Verified 2026-09-01 against the OpenAPI schema Vero embeds in its own docs
(`help.getvero.com/api-reference/*`, `originalFileLocation: "api-reference/track/track.yml"`) and
confirmed live: an unauthenticated `POST /users/track` returns
`401 {"status":401,"message":"Invalid authentication: You must provide a valid auth_token to
access this resource."}`.

There is no dedicated ping/whoami endpoint — the Track API is write-only. `test` sends the same
`POST /users/track` the `identify` action uses, with a fixed test id (`w6w-connection-test`) and
`extras.update_only: "true"` — Vero will only *update* a profile with that id if one already
exists, never create one, so repeated connection tests never mint a fake customer.

## Actions

| Key | Endpoint | Notes |
|---|---|---|
| `identify` | `POST /users/track` | `id` and `email` both required (per the Getting Started guide). Creates or updates (upserts) a profile. |
| `track` | `POST /events/track` | `eventName` required; at least one of `id`/`email` required. |
| `edit-tags` | `PUT /users/tags/edit` | `add`/`remove` string arrays; at least one required. |
| `alias` | `PUT /users/reidentify` | Changes a user's `id` to `newId`. Vero calls this advanced/irreversible. |
| `delete` | `POST /users/delete` | Permanent. Not recoverable. |
| `resubscribe` | `POST /users/resubscribe` | Global resubscribe. |
| `unsubscribe` | `POST /users/unsubscribe` | Global unsubscribe. |

All seven verbs were verified 2026-09-01 against the OpenAPI request/response schemas Vero embeds
in each endpoint's own doc page (readable in the page's server-rendered HTML even though no static
`track.yml`/`openapi.json` is reachable directly — see "How this was verified" below), and the
generic API Overview page (base URL, error shape, auth mechanism).

### `identify`'s `preferences.topics` is deliberately omitted

The `POST /users/track` request schema also accepts a `preferences.topics` array to
subscribe/unsubscribe a user from specific preference-center Topics (by topic `id` or `name`).
This app leaves it out: resolving or creating a Topic is a Campaigns API operation (`POST /topics`,
`GET /topics`), which this app does not implement (see above). Wiring `preferences.topics` without
a way to look up valid topic ids/names would mean asking a workflow author to hand-type an opaque
numeric id from a UI this app can't reach.

### `channels`/`data` are free-form JSON

`identify`'s `channels` (push device tokens) and `data` (profile properties), and `track`'s `data`
(event properties), are open-ended per the schema. Each is exposed as a single `type: "json"` param
that's passed straight through — no lossy re-interpretation in between.

### `phone_number` is not implemented

The JavaScript SDK's `user.identify()` example includes a `phone_number` convenience field (used as
the SMS delivery address for Journeys), but the REST `POST /users/track` request schema this app
calls does not list it as a property. Rather than guess whether the SDK maps it into `data` or a
field the REST schema's auto-generated docs simply omitted, this app leaves it out.

### Idempotency

| Action | `idempotent` | Why |
|---|---|---|
| `identify` | `true` | A POST with the same id/email/data is a pure upsert; Vero also rejects a change older than what it already has for a property. |
| `track` | `true` | Vero documents an automatic 5-minute dedupe window keyed on `auth_token` + `event_name` + `identifier` + (`data` or a `check_id`) — a retry that resends the identical call converges on the original event. Different from vendors (e.g. Customer.io) whose Track API has no such native dedupe. |
| `edit-tags` | `true` | Set-membership operation; adding/removing an already-(un)set tag is a no-op. |
| `alias` | `false` | A successful call retargets `id` onto `newId`; a retry against the stale `id` no longer resolves. |
| `delete` | `true` | Deleting an already-deleted (or nonexistent) id reaches the same end state. |
| `resubscribe` | `true` | Set-membership operation. |
| `unsubscribe` | `true` | Set-membership operation. |

## How this was verified

`help.getvero.com` (the redirect target of `developers.getvero.com/?bash`) is a Mintlify-hosted
docs site. Its `/api-reference/openapi.json` is Mintlify's own unmodified sample spec ("OpenAPI
Plant Store") — not Vero's real API — and no static `track.yml`/`campaigns-v2.yaml` is reachable
directly. Vero's actual OpenAPI schema for each Track API endpoint is embedded, server-rendered,
inside that endpoint's own doc page (e.g. `/api-reference/users/identify`) as the page's
React-Server-Components payload, including full `requestBody`/`responses` JSON Schema, example
values, and the endpoint's `security` scheme. Every action and the auth method above were verified
against that embedded schema, cross-checked against the prose guides (`llms-full.txt`) and
confirmed live against `https://api.getvero.com/api/v2` (base URL, error shape, and the absence of
rate-limit headers).

## Health check

Three different questions get confused with each other, so this section keeps them apart: is the
*vendor* up, is *this credential* live, and do we have *quota* left.

### Is the vendor up?

**Service status** — <https://status.getvero.com>. Confirmed live 2026-09-01 as a genuine, claimed
Atlassian Statuspage (`page.name: "Vero"`, `page.id: "t4s7kx6qh253"`), tracking 22 components. None
is named exactly "Track API" — the closest match is "Vero 1.0: Ingestion API", the legacy name for
the same stable endpoints this app calls — so rather than pin the check to a component name that
may drift, it reports the page-level indicator plus every component's own state.

```
GET https://status.getvero.com/api/v2/summary.json
```

Unauthenticated, cheap to poll, identical for every Connection, so the check runs once
(`scope: "app"`) and the result is shared.

### Is this credential live?

This is what the Auth `test` hook does — the app's own health check, and the only one of the three
it performs itself. See [Auth — Tracking API Key](#auth--tracking-api-key) above.

### Do we have quota left?

**Declared unavailable, honestly.** Neither the API Overview nor any Track API endpoint page
documents a rate-limit header or proactive quota surface, and a live, unauthenticated
`POST /users/track` on 2026-09-01 returned no `X-RateLimit-*`/`RateLimit-*`/`Retry-After` header on
its `401` response. Vero's docs mention "rate limits" only for its MCP surface (a different API
this app does not call). Rather than fake a check or silently omit one, `health/quota.ts` declares
`unavailable` with the reason, per
[`rfcs/healthcheck.md`](https://github.com/w6w-io/w6w-core/blob/main/rfcs/healthcheck.md)'s
"declare absence" pattern — `severity: "informational"` so a permanent `unknown` never worsens this
App's roll-up verdict.

## Declared health checks

| Key | Kind | Scope | Credential | Severity | Min interval | Probe |
|---|---|---|---|---|---|---|
| `service` | service | app | none | degraded | 60s | `health/service.ts` |
| `quota` | quota | — | — | informational | — | declared `unavailable` — no probe exists |
| `auth:api-key` | credential | connection | signed | fatal | — | derived from the `api-key` auth method's `test` hook |

The host `status.getvero.com` (for `service`) is reachable **only inside that hook's worker** — not
from any action, and not from the other checks. The spec allows the widening precisely because the
check is unsigned; pairing an extra host with `credential: "signed"` is rejected at load time, so a
credential can never reach a status host.
